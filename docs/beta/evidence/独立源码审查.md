## Validated issue 1 — P1: submit ancestor bypasses custom click safety

Initial affected hash: public and extension `autofill/engine.js`, SHA256 `380d6459c8cd21377a443152b59efda5e3961142d512d51eb033ccb9feb626bc`. Initial locations: `public/autofill/engine.js:26-29` (member gate), `:39-42` (trigger gate), `:198` and `:213` (click sinks); mirrored extension file is identical.

The safety check rejects submit buttons when they are the option itself or descendants, but a span nested inside an ancestor submit button passes. A click on that span activates its ancestor's native submission behavior. A combobox span nested inside a submit button has the same problem when the engine opens the list. This is browser default behavior; the fixture's submit listener only calls preventDefault and increments a counter. It does not submit from a custom click handler.

Fresh headless installed Edge, isolated new browser, ephemeral loopback server (port 0), actual production rules/engine loaded, no existing QA processes used:

```html
<form><div class="form-item"><span class="form-item__text">现居城市</span>
<div class="phoenix-select" data-value=""><button type="button" aria-controls="opts">请选择</button>
<div id="opts" role="listbox"><button type="submit"><span role="option" data-value="hz">杭州</span></button></div>
</div></div></form>
```

`scan()` returned `custom-select`; apply of `{fieldId:'f0',value:'杭州',choice:{path:'contact.city'}}` returned `filled:0, failed:1, automaticSubmitRequested:false`, while the fixture observed `submits:1`.

```html
<form><button type="submit"><span role="combobox" aria-label="现居城市" aria-controls="opts"></span></button>
<div id="opts" role="listbox" hidden><div role="option" data-value="hz">杭州</div></div></form>
```

The same apply request returned `pending:1`, while the fixture observed `submits:1`.

Impact: filling a supported-looking custom control can finalize a real application, contradicting the explicit no-final-submission contract. Minimal remedy: a shared conservative gate for actual click targets that includes interactive ancestors, for both triggers and members; reject unsafe structures before any click. Add option, radio, and trigger ancestor regressions. Root and engine owner have received exact repros and accepted the issue.

## Validated issue 2 — P2: cross-origin recovery append loses a draft

Initial locations: `public/autofill/profile-ui.mjs:92` (Web-Lock read/modify/write), `extension/bridge-policy.mjs:31-32` (individual queue operations), `public/autofill/vault.mjs:33-34` (shared routing). Extension profile UI mirror is identical.

Web Locks are origin-scoped. Extension options and a shared workbench page have different origin locks even when both use VAULT_KEY as the lock name. Their recovery append reads the canonical whole draft list, appends locally, then replaces that list. CanonicalStore only serializes each separate get/set, so two readers can both read an empty list and both successful writes replace it. UI may then clear both plaintext drafts and report both recoveries as durable.

Deterministic local repro used the actual CanonicalStore/addRecovery APIs and an in-memory structured-cloning storage adapter, with two existing-policy-valid encrypted draft envelopes. Result:

```json
{"initial":[null,null],"commits":["fulfilled","fulfilled"],"retainedIds":["workbench-unsaved"]}
```

Impact: one unsaved draft silently disappears when workbench and extension lock concurrently; a read/modify/write can also resurrect a previously consumed draft if it overlaps a master commit. Minimal remedy: queue a canonical atomic recovery append/remove operation with master commits, or draft-list CAS with retry; retain count/size validation. Root has accepted and owns this fix.
